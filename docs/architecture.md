# The architecture

*What the system is, why it is shaped this way, and the one place the shape
breaks. Written 2026-09-03 to replace a document that had the same name and a
different job — see the note at the end.*

**Every size in this file is counted by `tools/tiers.mjs` and checked by
`npm run gates`.** No number here is typed by hand, because the version of this
document that typed them was wrong in every row within three weeks.

---

## 1. One principle, applied everywhere

**The whole system is pure functions over immutable data.** That is not a style
preference; it is the product promise made structural. This site's claim is
*check our work* — so every number on screen has to be re-derivable by the
reader from data they can fetch, using code they can read.

Three consequences follow, and each is visible in the tree:

**No server computes a number.** The pipeline writes immutable JSON to a CDN;
the browser derives every metric from it. There is no endpoint that could answer
differently tomorrow.

**A metric is a reducer over the event stream.** `src/lib/layer.js` states the
contract — a layer returns `{counted, surprising, excluded}` and accounts for
every event exactly once — and ships `conservation()`, which is a property test
rather than a convention. `excluded` holds ids rather than counts, deliberately:
you can balance a ledger of totals while losing track of which events they were.

**One implementation, two callers.** The reducers run unchanged in the browser
and in `builders/measure.mjs` at pipeline time. When the plan of record put the
archive computation in Python, that was rejected as a second implementation of
the domain rules in a second language — the reasoning is in `measure.mjs`'s own
header, and §4 records what it cost us the one time we did it anyway.

## 2. The one exception: `src/app.js`

Everything above is pure functions over immutable data. **`app.js` is a state
machine that does not admit it is one**, and that is the single genuine
architectural inconsistency in the project.

The shape of it: **module-level mutable bindings, no exports**, one very large
reader (`render`, which touches eleven of those bindings across 328 lines), and
writers scattered across the file. There is no interface, so there is nothing to
assert against.

**This is not a size complaint, and the distinction matters because it changes
the fix.** Three things follow from the state, none of them from the line count:

- **It is invisible to coverage.** The test harness loads it with `new Function`,
  and a string compiled at runtime is never a file, so no instrument can see it.
  The project's published coverage figure is therefore *a rate computed without
  its largest and most-changed file*.
- **Every seam defect this project has had lives here.** Not because the file is
  long — because two things that had to agree had nowhere to be checked. They are
  one class, not a run of incidents.
- **Splitting it into seven files would make it worse.** The natural clusters are
  visible (ice-drawing, announcement, transport, the work panel, layer controls,
  the why-popup, boot/geometry), but they share the same mutable bindings. Seven
  files mutating the same globals scatters the writers and destroys the one
  property the single file still has: the state is auditable in one place.

**The fix, when there is appetite for it, is to make the state explicit** — one
state object, `render(state)` as a function of it, writes through a single
setter. Not a framework; the same code, differently shaped. The value is *the
enforced write path*, not the container: renaming the bindings to `S.trails`,
`S.hdOn` and leaving the writes scattered is globals with a prefix, and this
project has a name for that kind of change.

⚠️ **Two things that sound like one and are not.** Making the state explicit does
not deliver coverage, and coverage does not require it. The coverage hole is
caused by `new Function`; it is fixed by changing how the harness loads the
bundle. Do them separately or the expensive one gets credit for the cheap one's
result.

## 3. Decisions a reviewer will assume are oversights

Every unusual decision in this repo has its reasoning written down somewhere.
These four are the ones most likely to be read as carelessness, so they are
collected here.

### 3.1 No framework, and pages are built by string concatenation

Python builders emit HTML; `app.js` writes `innerHTML`. There is no template
engine, no JSX, no client-side router.

**Why it holds:** the shipped artifact is byte-identical from source and gated
that way (`build_main.py --verify`), so the output is checked as a whole rather
than trusted per-component. A framework would put a layer between the code a
reader inspects and the bytes a browser receives, on a site whose entire pitch
is that those are the same thing. The page also ships with **zero runtime
dependencies**, which is a promise about what reaches a browser.

**What it costs:** no component boundary, and `innerHTML` assembly is easy to get
subtly wrong. That cost is paid by the gates and by `tools/pixels.sh`, because
the unit suite is blind to layout by construction.

### 3.2 The browser bundle is a regex concatenator

`build_main.py::_inline` strips `import`/`export` with a regex and concatenates
`src/lib` in a hand-ordered list, so the whole bundle is one lexical scope.

**Why it holds:** the page is one file with inline script pinned by CSP hashes,
and this needs no bundler, no build-time module resolution, and no dependency.

**What it costs, stated plainly:** no JavaScript tool can see this project's real
dependency graph. `madge` reports 11 orphan modules and `knip` 17 unused exports,
**13 of which are used in production** — the tools are reading a source tree the
browser never receives. Treat their output on `src/` as unreliable by default.
The module order is no longer hand-asserted; `test/build.test.js` derives it from
the real imports.

### 3.3 The Python↔JS data contract is checked by sample, not by schema

There is no declared list of event fields. `extract.py` writes the record and 26
JS modules read it.

**Why it holds, and this one is genuinely contrarian:** a declared schema would
be a *second statement of the truth*, free to drift from the extractor that
actually produces the data — which is this project's single most-repeated
failure. Instead `test/fixtures.test.js` asserts cross-fixture consistency: a
field every event of a type carries in one fixture and none carry in another is
not a fact about two games, it is two vintages of extractor in one directory.

**Its blind spot is stated rather than discovered:** if every fixture were stale
at the same vintage, it says nothing. Mixing is what it catches, and mixing is
how fixtures are added.

### 3.4 Values the league controls are guarded where the archive is walked

A rule derived from a sample is still a sample, so a check that holds last
season's answer in a unit test is not a check. Vocabulary, club names, game
types and situation codes are alarmed on **drift, at archive scale**, in the
pipeline — loud there, never in the artifact, because the measures are correct
and what is missing is a name.

## 4. What this shape has actually cost, twice

Two findings, both closed, recorded because they are the evidence for §1 rather
than opinions about it.

**`strength.js` held eight literal situation codes** whose own comment said
"This game shows five" — a rule derived from one game, which had already gained
codes twice. `extract.py::situation_ok` is the same domain rule in Python, was
corrected to decode the digits, and *names that very list as its precedent*.
Only the Python half was ever fixed. Over the fixtures that silence cost 91
refused events, 44 of them 3-on-3 overtime, and the ledger told readers *"game
state not recorded for this event"* about a state the league had recorded. Both
implementations are now checked against each other exhaustively over all 10,000
codes, and the archive alarms on any code we decline without naming.

**The lesson generalises:** the defect was invisible to every mechanical
instrument. Complexity, duplication, dead-code, lint, coverage and mutation
scores were all clean on it, because the code was impeccable and the *claims*
were false. **This project's quality is the truth of its claims; the metrics
measure the substrate.**

## Note on this file's predecessor

The document that held this name was written 2026-08-11 to answer one question —
*are we shoe-horning new functionality into modules that should not carry it?* —
and it answered it well. But it was **a review of a specific plan wearing the
name of a description of the system**, so a reader opening it to learn the shape
found an argument about a change instead, and every size in it had drifted: the
analysis tier read 1,065 against an actual 5,469.

Its findings were acted on and are not lost; what it argued for — one
implementation of each rule, called from both tiers — is §1 of this file and is
now how the system works. The reasoning lives in `docs/status.md` and in the
module headers, where it is next to the code it describes.
